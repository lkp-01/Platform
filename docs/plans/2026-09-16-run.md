# Run Implementation Plan

**Goal:** 在现有版本归因基础上，把一次 Agent 任务统一为可查询、可取消、有明确结果的五态 Run。

**Architecture:** Platform Runtime 管理 Run 生命周期与持久化，通过现有 Cordis 插件、Session Controller 和 Session 事件适配 DeepSeek Harness；Harness 继续拥有唯一的 Agent Loop。保留已有 Agent → Version → Run → Session 关联，不新增独立执行循环。

**Tech Stack:** 当前仓库 TypeScript、Cordis、Storage Domain、Typert Remote、React、Vitest 和 Web E2E。

**状态：** 2026-09-17 已实施，交付与验证结果见 [Run 验收记录](../run-acceptance.md)。以下保留原计划及范围约束。

## 1. 产品边界

一个 Run 表示用户提交的一次任务，包括其中全部 LLM/Tool 循环，直到成功、失败或取消。首版一个 Run 对应一个独立 Harness Session；Run ID 与 Session ID 保持不同概念。

Run 回答：哪个 Agent、哪个版本、谁发起、何时创建/开始/结束、当前状态、运行耗时、输入、最终输出或错误，以及是否可以取消。

本期包含：创建、版本绑定、五态状态机、生命周期持久化、列表/详情、取消、统一事件关联、历史兼容和测试。

本期不包含：自动 retry、checkpoint、resume、任务队列、分布式 worker、执行并发限额、调度、心跳/租约、完整 RBAC、Eval 产品页面。按 Run 串行处理状态更新是保证数据正确性的必要措施，不是执行并发控制功能。

## 3. 方案选择和职责

推荐：保留现有插件装配，把 `platform-runs.ts` 扩展为 Runtime 用例层，按职责提取小模块。仍使用 `platform_agent_runs`，不强制更换存储后端。

备选一：继续只读投影 Session。改动较少，但启动失败、取消请求、查询性能和平台时间字段难以形成稳定契约。

备选二：独立 Runtime 服务和新数据库。边界更物理化，但当前单 Host 阶段会引入部署、通信和分布式一致性问题，超出本期。

| 层 | 职责 |
|---|---|
| Registry / Version / Deployment | 校验资源、提供不可变配置、解析当前默认部署 |
| Platform Run / Runtime | 接受任务、冻结关联、状态转换、持久化、取消、结果摘要 |
| Harness adapter | 准备版本 Preset、创建 Session、提交一次任务、调用取消、解释 Harness 结束原因 |
| DeepSeek Harness | LLM/Tool 循环、原始执行事件、Session 持久化 |
| Observability / Evaluation | 消费相同 runId/versionId/sessionId 及生命周期事件，复用 Harness 明细 |

预计无需修改 core/agent-loop。实施时先读取涉及目录的 AGENTS.md，验证现有扩展点；若确实缺少扩展点，先说明原因与最小改动范围。

## 4. Run 契约

保留现有 `id`（即产品中的 run_id）、agentId、agentVersionId、versionNumber、platformWorkspaceId、configHash、deploymentRevision、sessionId、createdBy、createdAt。

新增或调整：

```typescript
type RunStatus = 'PENDING' | 'RUNNING' | 'SUCCEEDED' | 'FAILED' | 'CANCELLED'

interface RunLifecycleFields {
  status: RunStatus
  startedAt: string | null
  finishedAt: string | null
  cancelRequestedAt: string | null
  input: { prompt: string } | null // 旧数据无法恢复时允许 null
  result: {
    textPreview: string | null
    sessionId: string
    finalMessageSeq: number | null
  } | null
  error: { code: string; message: string } | null
}
```

- actor 从服务端取得。当前只有 shared-host 身份，如实展示 shared-host；不把客户端提供的名字当认证用户。
- 新 Run 的 input 必须保存；result 只保存有界摘要与原始消息引用，完整对话/工具事件仍在 Session。
- 成功但无文本输出允许 result.textPreview 为 null；不得拿最后一条工具消息或推理内容冒充最终答案。
- 内部增加记录格式标识、最后已处理 Session 事件序号、必要的转换序号；这些不是用户可编辑字段。
- `startedAt` 取任务实际进入 Harness turn 的时间，`finishedAt` 取结束事件时间；准备失败可保持 startedAt=null。
- `durationMs` 为派生值：RUNNING 使用服务器当前时间减 startedAt，终态使用 finishedAt 减 startedAt；未开始为 null。页面显示等待时间时使用 createdAt 单独计算。
- 所有时间存 UTC，页面按本地时区展示。历史时间缺失显示未知，不用 createdAt 或迁移时间伪造执行时长。

## 5. 状态机与结束原因

```text
PENDING ──→ RUNNING ──→ SUCCEEDED
   │            ├────→ FAILED
   │            └────→ CANCELLED
   ├─────────────────→ FAILED
   └─────────────────→ CANCELLED
```

| 状态 | 含义 |
|---|---|
| PENDING | 已持久化接受，正在准备或创建 Session，尚未开始任务 |
| RUNNING | Harness 已开始该任务 |
| SUCCEEDED | Harness 报告正常完成 |
| FAILED | 准备/启动/执行失败，或执行中断且未正常结束 |
| CANCELLED | 开始前已阻止提交，或 Harness 确认用户取消 |

统一经一个 transition 方法更新，按 Run 串行化并检查允许的源状态；终态不可回退，重复事件幂等，迟到事件不能把已结束任务改回 RUNNING。

Harness completed → SUCCEEDED；error → FAILED；用户导致的 aborted → CANCELLED；interrupted/Host teardown → FAILED，错误码为 EXECUTION_INTERRUPTED 等明确原因。具体 abort cause 以源码契约与集成测试核对，不把所有 abort 自动认作用户取消。

工具单次报错并不等于 Run 失败；Harness 能继续处理并完成任务时 Run 仍为 SUCCEEDED。SUCCEEDED 表示执行完成，不表示业务答案已通过 Eval。

## 6. 创建与执行顺序

1. 验证输入、Workspace、Agent 状态和 requestToken；没有部署、跨范围访问等无效请求直接拒绝。
2. 在现有 admission 临界区内处理 token 去重并冻结当前 deployment/version，持久化 PENDING、输入和 Session ID。
3. 接受成功后返回 Run；在同一 Host 受生命周期管理的异步任务中准备版本产物、创建 Session。无需引入任务队列或 worker。快速执行可能让首次响应已经是 RUNNING/终态，客户端不能依赖必定观察到 PENDING。
4. 保留已有 `platform/run` 归因写入并 flush；在任何提交任务的路径之前检查是否已取消。
5. 向 Harness 提交且只提交一次用户任务；监听 turn/start、turn/end 和必要的消息事件，更新 Run。
6. 保存最终输出引用或错误、结束时间和终态，并释放临时监听/启动句柄。

当前 prepare(version) 在 Run 落盘前执行，需移至接受之后，让版本产物准备失败也能留下 FAILED Run。首次落盘失败绝不能启动 Harness；accepted 后失败必须可由同一 runId 查询。

同 token + 同输入返回同一 Run，不重启、不重新选择部署；同 token + 不同输入返回冲突。保持当前幂等能力，不把它扩大成自动执行重试。归档后不接受新 Run，已接受任务可按固定版本继续。

## 7. 取消语义

新增 `runCancel(workspaceId, agentId, runId)`，返回更新后的 Run。

- PENDING：持久化取消意图，与启动阶段共享每 Run 的状态保护；确保没有 followup 才可进入 CANCELLED。如果 Session 创建已经开始，待创建返回后清理资源并阻止任务提交。
- RUNNING：保存 cancelRequestedAt，调用 Harness 取消；状态暂仍 RUNNING，UI 显示“正在取消”。收到用户取消的结束事实后才进入 CANCELLED，不增加第六种状态。
- 已终态：重复取消返回原终态，不覆盖结果。
- 取消和完成竞争：以串行处理并持久化的实际结束事实确定终态。请求取消不保证成功；自然完成先发生则保持 SUCCEEDED，不能因晚到的点击覆盖成功。
- 取消调用失败要向调用方报告，不能显示取消成功；允许再次请求。非协作工具仍在运行时不提前宣称已停止，不承诺撤销已发生的外部副作用。
- 受管执行页调用同一个 Run 取消入口。原普通 Session 取消保持现有行为；兼容入口产生的 Harness 取消事件也应收敛到同一 Run。

## 8. 持久化、公共事件与重启

Run 表保存平台生命周期事实及有界状态转换记录；Session 保存原始 LLM/Tool/消息明细。生命周期记录使用统一 eventId/runId/agentId/versionId/sessionId/occurredAt 契约，可表达 run.created、run.started、run.succeeded、run.failed、run.cancelled。取消请求作为辅助事实，不是终态。

同一 Run 记录中的状态和转换记录一次更新，成功后再发进程内通知；不为 Observability 和 Eval 分别建执行表。本期不提供分布式事件总线或可靠消息投递，消费者可通过同一持久化记录查询事实。

`session/event` 是同步通知，不等于磁盘提交已完成。监听器只登记待处理事件，通过受管异步处理保存投影；不能在通知中无保护地 fire-and-forget 或阻塞 Harness。完成投影需明确 Session flush 与 Run 更新顺序，记录源事件序号，覆盖 flush/Run 写入失败的测试。

列表主要读 Run 索引，不为每条 Run 重读完整 Session。收到事件、重启或发现缺失投影时才做有界对账；终态摘要在重启后可直接查询。

单 Host 启动时处理遗留非终态：

1. 先读取持久化 Session 完成事实，已有正常结束则补齐对应终态和结果。
2. 确认没有活跃启动/执行句柄、也没有完成事实的旧任务，标记 FAILED / EXECUTION_INTERRUPTED，不自动重发输入。
3. Session 不存在与读取失败分别处理：存储读错误不能伪造执行失败事实，应暴露存储故障并保留记录。
4. 若真实结束时间不可知，用中断检测时间作为平台关闭记录的时间，同时标明时间依据；页面不把它显示为精确执行耗时。

这些是状态对账，不是 resume。插件重载时若 Harness 仍有对应活跃 Agent，不得误判为进程中断。

## 9. 历史数据兼容

使用兼容读取 Schema 和记录级格式标识，让旧、新 Run 能在原 Domain 中共存；不要只把 Domain version 从 1 改为 2 导致旧数据无法打开。若采用存储层版本升级，必须先验证现有 JSON/SQLite 后端的实际兼容机制。

- accepted/running 记录不能只改大小写：当前旧表多数仍存 accepted，即使任务早已结束，需结合原 Session 事实补齐状态。
- succeeded/failed/cancelled 映射到对应大写状态；interrupted 映射 FAILED 并保留中断原因。
- 旧 error 字符串转换为结构化错误；能从原 Session 还原的输入、开始/结束时间和结果才回填，其余保留未知。
- 每条迁移可重复执行、失败不丢记录；保留 Run ID、token 去重身份、版本绑定和原 Session 链接。
- 不给普通历史 Session 伪造 Platform Run 或 Agent Version。

## 12. 验证清单与命令

## 13. 完成标准

用户点击 Run Agent 后获得持久化 Run；它固定 Agent Version，依靠原 Harness Loop 执行；列表与详情能准确回答发起者、状态、时间、输出/错误；可在待启动或执行中取消；刷新与重启不会丢失历史或自动重新执行。只有五种公开状态，终态稳定，既有 Version 与普通 Session 相关行为回归通过。

实施采用现有 PlatformRuns 承载适配与存储用例，状态机与 Schema 独立成模块；真实 Harness 集成与 API 场景复用现有 Loader 组合测试。具体交付、文件落点与环境限制见验收记录。
